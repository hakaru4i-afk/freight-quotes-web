# Проверка готовности 1.19.1 — 01.11.2026

## Решение
Выпуск заблокирован: критические сценарии ролей, серверные права и экспорт не прошли функциональную проверку. Production не изменялась. Флаг maintenance сохранён. Публикация облачной среды ранее не является выпуском приложения.

## Проверенные факты
- Работа ведётся в codex-development с документацией из 62bd09a; main на момент чтения удалённых ссылок — 0551b1f.
- Оба реальных GET /functions/v1/freight-api/health вернули 200, ok=true, release=1.19.1 и соответствующие environment/projectRef.
- Оба анонимных GET /api/access вернули 403 «Войдите в кабинет». Это ожидаемый отказ, а не доказательство неисправности авторизации.
- Локальные frontend: production 1.19.0 с maintenance=true; staging 1.19.1 с maintenance=false. История связывает включение баннера с fc4aa9a, а последние frontend-изменения ограничены staging. Причина несоответствия файлов подтверждена; причина прерывания организационного процесса выпуска неизвестна.
- Node проверил синтаксис обеих app.js. Проверены размеры и SHA-256 всех 20 OCR-ресурсов и хеши app.js/style.css в HTML.
- Chromium отрисовал обе локальные версии при 1440×900 и 390×844: нет pageerror и горизонтального переполнения. Эти проверки не проверяют рабочие кабинеты.
- Запросы API из localhost блокируются CORS: для localhost отсутствует Access-Control-Allow-Origin, для https://hakaru4i-afk.github.io сервер возвращает этот origin. Не следует отключать защиту браузера или TLS ради теста.
- В доступной истории Git отсутствуют исходный frontend, package.json, сборочная система, sourcemap, backend и миграции. Старые отчёты о коде Supabase не заменяют текущего доступа к нему.
- Поиск репозиториев и Pages через GitHub API возвращает Forbidden. Native Git read работает. Это разные области доступа.

## Изменения
Усилен scripts/check_release_config.mjs: проверка API ref внутри JS, хешей CSS/JS в HTML, размеров и SHA-256 OCR; добавлен --target=1.19.1. Строгий режим отвергает несовпадение целевого релиза и включённое обслуживание. Это проверка артефактов, а не разрешение на деплой.

## Безопасное продолжение и откат
1. Подключить репозиторий исходников и backend с проверяемой принадлежностью, предоставить поддерживаемый способ тестовой авторизации через безопасные настройки (секреты не в чат).
2. Выполнить положительные и отрицательные сценарии всех ролей только на изолированных staging-данных. Исправить обнаруженные ошибки в исходниках, собрать staging и повторить проверки.
3. До production зафиксировать точный актуальный main, сохранить проверяемый архив артефактов вне checkout и проверить восстановление в локальной копии. Сейчас отдельная резервная копия и проверка восстановления не выполнены; история Git не является резервной копией БД.
4. Собрать production из тех же исходников с production ref; не копировать test/app.js напрямую. Проверить совместимость без изменения реальных данных.
5. Только после критических тестов опубликовать frontend, проверить реальный сайт, затем снять maintenance и повторить проверки. При регрессии восстановить предыдущие production-артефакты отдельным обратимым коммитом; БД не переносить из staging.

Изменения приложения и серверных функций, релизные коммиты в main, миграции, публикация и снятие баннера не выполнялись. Версия live frontend не подтверждена чтением опубликованного сайта; локальные production-артефакты — 1.19.0, реальные health API — 1.19.1.
