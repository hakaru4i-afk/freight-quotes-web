## Что НЕ следует делать

- Не заменять production `app.js` тестовым `test/app.js` напрямую: у них разные ссылки на Supabase, а тестовая сборка не предназначена для рабочей базы.
- Не редактировать `main`, `site-status.json` и базу production без отдельного решения о выпуске или откате.
- Не объявлять обновление завершённым только по активности Edge Function; это не доказательство исправной работы форм, прав доступа и вложений.

## Безопасные варианты завершения

**A. Довыпустить 1.19.1** — предпочтительно после успешных тестов staging и нахождения исходной системы сборки. Собрать production 1.19.1 с **production Supabase ref**, проверить основные сценарии, выпустить код и метаданные, только затем установить `maintenance: false`. Нужна явная санкция на публикацию.

**B. Отменить предупреждение** — если выпуск 1.19.1 откладывается, оставить интерфейс production 1.19.0 и снять только `maintenance` после проверки работоспособности API 1.19.1 с UI 1.19.0. Это прекращает баннер, но **не выпускает** интерфейс 1.19.1. Нужна явная санкция.

## Минимальные проверки перед A или B

1. Прочитать опубликованные в GitHub Pages `site-status.json`, `build-info.json` и `index.html`; убедиться, что это действительно актуальный `main`.
2. Проверить `GET /functions/v1/freight-api/health` рабочей и тестовой сред. Факт `ACTIVE` в настройках Supabase недостаточен для проверки HTTP-ответа.
3. Проверить вход тестового пользователя каждого типа, запрос ставок, загрузку/чтение документов, согласование заявки, переход к `en_route`, экспорт PDF/Word/Excel и отсутствие ошибок прав доступа. **Использовать только тестовую среду и тестовые записи.**
4. Проверить разграничение ролей и невозможность читать/редактировать чужие заявки. Не передавать личные, коммерческие или реальные документы в демонстрационную среду.
5. Сначала получить отдельное подтверждение владельца на выпуск или откат; затем зафиксировать релиз и проверить исчезновение баннера.
6. Добавить `node scripts/check_release_config.mjs` к предрелизной проверке. Сценарий диагностический, ничего не публикует и не меняет.

## Дополнительные технические замечания

- Backend в обоих проектах находится в Supabase Edge Function `freight-api`; в каждой базе 60 таблиц схемы `freight`.
- Для обеих Edge Functions `verify_jwt: false`; обнаружен собственный серверный обработчик авторизации. Не менять флаг механически: нужна проверка действующего механизма сессий.
- В серверной проверке переходов этапов допускается переход `awaiting_loading -> en_route`, но перед ним в `/api/shipment-execution` запрашиваются согласование заявки, пакет документов, дата погрузки, фактическая дата выхода и проверка ВЭД/владельца. Требуется продуктовая проверка, должен ли сам отдельный этап «Погрузка» быть обязательным. **Это не подтверждённая ошибка безопасности.**
