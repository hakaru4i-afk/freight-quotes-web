# Правило полного функционального соответствия production ↔ test

**Утверждено владельцем 17 ноября 2026 года. Приоритет P0.**

## 1. Что должно совпадать

Успешная сверка номеров сборок **не является** подтверждением совпадения портала.

В утверждённом релизе оба окружения должны иметь одну и ту же бизнес-версию, пользовательские сценарии, восемь кабинетов (Owner и семь ролей), формы, поля, обязательность и сохранение значений, статусы, ограничения, оценку ставок, переходы процессов, чаты, документы, карту/геоданные, уведомления, FAQ по ролям, локализации RU/EN/ZH, визуальные стили, адаптивность и серверные права доступа.

**Различаются намеренно:** Supabase projectRef/URL, реальные данные, пользователи, сессии, ключи и секреты, тестовые идентификаторы, cache/build SHA, диагностика и изолированные тестовые записи. Базы и реальные документы не копировать между окружениями.

## 2. Два направления обновления

**Горячее исправление production:** исправить и проверить ошибку в рабочей среде, одновременно внести тот же функциональный патч в test; совместить UI, API, FAQ, права, миграции схем (если необходимы), тесты и реестры. Разница двух версий после исправления должна быть только технической. Если изменение backend/миграция несёт риск потери данных, сначала провести совместимость и безопасный откат.

**Разработка в test:** зарегистрировать задачу, реализовать и протестировать только в staging; пока идёт разработка, различие допускается **только как явно зарегистрированный staging-кандидат**, но **не считается утверждённым релизом**. После отладки и явного согласования владельцем перенести функционально идентичный набор в production, проверить роли, API и UI на обоих окружениях и закрыть кандидат. Без согласования — production не менять.

Нельзя молча допускать расхождения production и test. При любом незарегистрированном различии — дефект и запрет промоции.

## 3. Проверки выпуска

До публикации production обязательны:
- Сверка исходников **всех загружаемых UI JS/CSS** и главного `app.js` с разрешёнными различиями только в URL, сессионных ключах и техническом build/cache ID; несовпадение поведения = FAIL.
- Сверка API и ролевой матрицы, обязательных полей, статусов, workflow, RLS, схемы базы и Storage **без копирования пользовательских данных**.
- Браузерный E2E под разрешёнными временными QA-пользователями каждого кабинета, desktop 1440×900 и мобильный 390×844, включая RU/EN/ZH. 37/37 сценариев, ноль критических ошибок; статические проверки не заменяют авторизованный E2E.
- Отдельная read-only проверка production после промоции: фактически отданные файлы, endpoint health, сохраняемые поля, видимость кнопок и серверные роли.
- Сверка реестра обновлений/замечаний/разработок и инструкций по соответствующим ролям. Запись release pair с SHA frontend/backend и статусом `PASS / PARTIAL / FAIL / BLOCKED`.

`scripts/check-runtime-parity.mjs` в обычном режиме **требует полного совпадения**. В стадии разработки допускается `--allow-staging-candidate` **только** с зарегистрированным файлом `test/development-candidate.json`, где `environment: staging`, `state: IN_DEVELOPMENT`, `ownerApproved: false`, `promotionBlocked: true`, корректный `issueUrl` и `allowedDifferences` — объект `имя файла → SHA-256 текущей production-копии`. Отчёт тогда `STAGING_CANDIDATE_ONLY`, **не PASS и не разрешение на выпуск**. На шаге production promotion использовать только строгий режим, без исключений.

При текущем сопоставлении основных фронтенд-сборок `app.js` различия оказались только техническими (API projectRef, среда, сессионные ключи, кеширование, build ID). Это проверка кода, а не доказательство живой работоспособности всех ролей.

## 4. Запреты и контроль

Не менять одну среду и оставлять другую устаревшей после утверждённого выпуска; не маскировать различия `app.js` общим исключением; не сливать staged features в production автоматически; не проводить опасные SQL/удаление реальных заявок ради тестирования; не объявлять весь портал принятым до авторизованного E2E.

Ответственность: помощник выполняет доступные проверки и безопасные изменения самостоятельно, всё требующее защищённого браузера и реального прохождения ролей передаёт в Codex с подтверждением фактического запуска и анализом отчёта, а не только с созданием issue.
